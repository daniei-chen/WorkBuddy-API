# 出站并发与连接池车道

Issue #161 的根因与修法。报告人的现象是「大批账号显示已禁用，单号测活报
`请求异常: PoolTimeout`」——两件事，这里只讲第二件（第一件是上游对
`11140 request illegal` 的判定，见 #201）。

## 现场：测活是被饿死的，不是病因

`refresh-credits` 会对**全部账号**并发取数（账号页加载与「刷新积分」按钮都走它），
而所有请求共用同一个 httpx 客户端 —— 客户端按「超时 + 代理」缓存，缓存键相同就共用
一个连接池（`config.http_client` 的借用语义）。httpx 默认池上限 100 条连接。

以前这个扇出**没有并发上限**：账号一多就把池占满，后面的请求排队，排队超过 pool 超时
（`WB_TENCENT_TIMEOUT`，默认 15 秒）就抛 `PoolTimeout`。单号测活借的是同一个池，于是
它排在队尾 —— 用户看到的就是「点测试 → 报 PoolTimeout」，而真凶是那批批量请求。

对比一下其它批量入口，它们早就有信号量：全部签到 5、刷新令牌 3、补偿领取 5。
只有刷积分漏了。

## 修法

1. **给扇出加上限**：`WB_CREDITS_CONCURRENCY`（默认 8，按页面的实际节奏取），
   `refresh-credits` 的每次取数都要先拿信号量。
2. **交互操作走独立车道**：`config.http_client(..., lane=...)` 把 lane 拼进缓存键，
   于是「测活」有自己的池，批量任务再挤也挤不到它。目前只有 `probe_account` 用
   `lane='probe'`——它是唯一「用户正盯着屏幕等结果」的账号出站动作。
3. **把 PoolTimeout 翻译成人话**：`PoolTimeout: timed out` 只会让人以为网慢，现在报
   「本机并发请求过多，连接池排队超时」并指出可调小 `WB_CREDITS_CONCURRENCY`。

## 调参建议

账号几十个时不需要动。**100+ 账号**且经常点「刷新积分」时，可按出口质量调整：

| 变量 | 默认 | 说明 |
|---|---|---|
| `WB_CREDITS_CONCURRENCY` | 8 | 刷积分同时查几个号 |
| `WB_CHECKIN_CONCURRENCY` | 5 | 全部签到同时签几个号 |
| `WB_REFRESH_CONCURRENCY` | 3 | 一键刷新令牌同时刷几个号（刷新接口最敏感） |

调大更快，但更接近腾讯风控的阈值；调小更稳，但账号多时前端可能等到超时。这三个都只影响
**本面板自己发起的**调用，不影响网关转发的对话流量（那条路由上游负责）。
