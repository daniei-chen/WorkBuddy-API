**核心问题**：IP 管控与登录防爆破此前可被伪造 `X-Forwarded-For` 绕过 ——

### 二、高危问题（已修复）

#### H1. 伪造 `X-Forwarded-For` 绕过 IP 管控与防爆破

**危害**：攻击者可冒充任意 IP，从而

- 绕过**入站 IP 白名单 / 黑名单**（`code=ip_blocked` 形同虚设）
- 绕过**每密钥 IP 白名单与 IP 数量上限**
- 绕过**登录失败锁定**（每次换一个伪造 IP，5 次锁定永不触发，
  密码可被无限爆破）

**验证证据**（修复前，实测）：

```
伪造 XFF=9.9.9.9（已在黑名单）      -> 200   ← 应被拦截却放行
密钥白名单=9.9.9.9，XFF=1.2.3.4     -> 403   ← 任意伪造任意 IP
8 次错误密码（每次换不同 XFF）        -> 全 401，未出现 429
```

**根因**：`client_ip()` 直接取 `X-Forwarded-For` 的**第一个**值。
但 nginx 配置为：

```nginx
proxy_set_header X-Real-IP $remote_addr;                      # 覆盖，可信
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 追加，首段可伪造
```

**修复**：

- 优先采用 `X-Real-IP`（反代以 `$remote_addr` 覆盖写入，不可伪造）
- 退化到 `X-Forwarded-For` 时，从**右往左**数第 N 个（N 由
  `WB_TRUSTED_PROXY_HOPS` 控制，默认 1）—— 右侧是反代追加的真实地址
- 新增 `WB_TRUSTED_PROXY_HOPS` 以适配前置 CDN 的场景

**修复后实测**：伪造 XFF 无法再骗过密钥白名单（403 且提示真实 IP）。

---

#### H2. 登录爆破仅按 IP 计数，换 IP 即可破解同一账号

**危害**：攻击者使用代理池（每 IP 试 4 次）即可对 `admin` 账号做
无限次密码尝试，永远不触发锁定。

**验证证据**（修复前）：8 次错误密码、每次不同 XFF → 无一次 429。

**修复**：改为**双维度锁定**

- 按 IP —— 防单机爆破
- **按用户名** —— 防「换 IP 打同一账号」的分布式爆破
- 两者上限均为 5 次 / 10 分钟

**修复后实测**：连续换 IP 打 `admin` → 第 5 次起返回 429。

### 三、中危问题（已修复）

#### M1. 交互式 API 文档对公网暴露

**危害**：`/docs`、`/redoc`、`/openapi.json` 返回 200，
把**全部管理接口的路径、参数与数据结构**公开给任何未认证访问者，
便于攻击者摸清攻击面（如发现 `/api/accounts/refresh-credits` 这类
消耗上游配额的接口）。

**修复**：生产环境默认关闭（`docs_url=None` 等），
需要时设 `WB_ENABLE_DOCS=1`。**线上实测三个端点均返回 404**。

#### M2. 协议头信息泄露

**危害**：`/api/sysinfo` 无需认证即返回**服务器绝对路径**
（`auth_dir`、`upstream_base`），可用于推断部署结构与后续攻击路径。

**修复**：改为需登录，且仅返回服务名与版本。线上实测 401。

#### M3. 无请求体大小限制（内存耗尽风险）

**危害**：网关会把整个请求体读入内存。上游 workbuddy2api 有 8 MiB
限制，管理端却没有 —— 少数并发超大请求即可耗尽内存导致服务不可用。

**修复**：入口处校验 `Content-Length`，超过 8 MiB（与上游对齐）
返回 413，不再读取。实测 9 MiB 请求体 → 413。

### 四、低危问题（已修复）

| 编号 | 问题 | 修复 |
|---|---|---|
| L1 | 登录失败计数 `_fail` 字典**无容量上限**，攻击者用大量源 IP 可持续占用内存 | 加 `MAX_TRACKED=5000` 上限，超限先清过期项、仍超则重置（实测 2 万次记录后大小被限制在 4997） |
| L2 | 网关**无限流**，单个密钥被打爆会拖累整个账号池 | 增加每密钥滑动窗口限流（默认 120 次/分钟，`WB_GATEWAY_RATE_PER_MIN` 可调），超出返回 429；同时清理过期计数防字典膨胀 |
| L3 | 缺少安全响应头，点击劫持 / MIME 嗅探风险 | 增加 `X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy`、`Permissions-Policy`、CSP（线上实测全部生效） |

### 五、已验证安全（无需修改）

以下经实际测试确认，未发现可利用问题：

1. **路径穿越** —— 6 种编码变体（`../`、`..%2F`、`....//`、`%2e%2e`、
   反斜杠、`/static/../`）访问 static 目录之外的文件，**全部 404**。
   线上实测亦为 404/400。原因：静态路由用 `Path.is_file()` 校验，
   且账号文件接口有独立的文件名白名单校验。

2. **认证绕过** —— 无 cookie、伪造 cookie、空 cookie、伪造
   `X-API-Key`、伪造 `Authorization`，**全部 401**。会话 Cookie 使用
   HMAC 签名，篡改即失效。

3. **越权访问** —— 对 `viewer` 只读角色测试 **11 个写接口**
   （删账号、改配置、建密钥、建用户、改安全规则、重启上游、修复统计、
   批量签到、清空日志 × 3），**全部 403**。

4. **凭据泄露** —— `/api/accounts` 不含 `accessToken`；
   `/api/settings/upstream` 不含明文 `api_key` 与 `raw` 字段；
   `/api/keys` 不含明文密钥（仅存 SHA-256）。

5. **会话安全** —— Cookie 具备 `HttpOnly` + `SameSite=Lax`；
   HTTPS 下自动加 `Secure`（依据 `X-Forwarded-Proto`）。

6. **密码存储** —— PBKDF2-SHA256，26 万次迭代，随机盐，
   比对使用 `hmac.compare_digest`（恒定时间，防时序攻击）。

7. **网关密钥** —— 仅存 SHA-256 哈希，明文只在创建时返回一次；
   前缀索引仅用于缩小查询范围，比对仍为恒定时间。

8. **端口暴露**（运维层面）—— 7863（上游）与 7864（管理端）
   均已改为仅监听 `127.0.0.1`，外网实测不可达，唯一入口为
   HTTPS 反向代理。

## 轮次二：2026-09-15 主动普查

本轮为**主动全面排查**（不是针对某个已知漏洞的修补），覆盖：鉴权与授权、注入类、
凭据保护、SSRF、路径处理、前端 XSS/CSRF、依赖与配置默认值、错误信息泄露。

结论：**发现并修复 2 处（1 中危 + 1 中危）**，其余检查项通过。下面按「查了什么 →
结论」逐项列出，便于复查与后续维护。

### 一、修复的问题

#### 1. SSRF：Upstash 连通性测试可探测内网与云元数据（中危）

**位置**：`server/services/wb2api.py` 的 `test_upstash`

**问题**：该接口把管理员填写的地址交给**服务端发起请求**（`POST {base}/ping`），
并把响应片段回显。地址归一化只抽取 host、不判安全性，因此可以指向：

| 输入 | 归一化结果 | 危害 |
|---|---|---|
| `http://127.0.0.1:7863` | `https://127.0.0.1` | 探测本机上游客关 |
| `169.254.169.254` | 同 | **云元数据**，常能取到实例临时凭证 |
| `http://metadata.tencentyun.com` | 同 | 腾讯云元数据 |
| `10.0.0.5` / `192.168.x.x` | 同 | 内网其它主机（横向移动） |

**为什么这算问题（而不是"管理员本来就能操作"）**：本仓库历史上真实发生过
「路径穿越 → 读到 secret → 提权改管理员密码」的入侵链。管理员权限往往是
**攻击链的中段成果**，而 SSRF 是拿到低权限后向内网横向的标准第二步。
纵深防御应当在能拦的地方就拦。

**修法**：不做域名白名单（会误伤自建/第三方 Upstash 兼容服务），改为
**排除回环、私有、链路本地、保留段、组播与已知元数据域名**；公网主机照常放行。
实现见 `_reject_internal_host`。

> 未做 DNS 解析后再校验：那会引入 TOCTOU（解析与请求之间结果可能变），
> 且每次测试多一次 DNS 查询。域名解析到内网的情形由部署方网络策略兜底。

#### 2. 数据库文件权限过宽（中危）

**位置**：`server/db.py` 的 `connect()`

**问题**：SQLite 库由 `sqlite3.connect` 默认创建，文件模式是 0644——
同主机其他用户或任何能读该目录的进程都能读走。库里存着：

- **API 密钥的哈希与前缀**（前缀可用于针对性爆破）
- 全部**请求日志**（来源 IP、User-Agent、模型、错误文本）
- **审计日志**（登录、改密、增删用户）

WAL 模式下还有 `-wal` / `-shm` 伴生文件，同样含未落盘数据。

**修法**：建库后把主库与两个伴生文件一并 `chmod 0600`。与 `users.json` 的
处理保持一致（那里早已收紧，因为存着签发会话的 secret）。

### 二、通过的检查项

#### 鉴权与授权
- **57 条 `/api` 路由逐条核对**：全部有 `current_user` 或 `require_admin`
- **所有写操作（POST/PATCH/DELETE）都要求 admin** —— viewer 无法越权写
- 未鉴权的仅 3 条，均属设计允许：`/api/login`、`/api/logout`、`/api/healthz`
- `/api/healthz` 与 `/healthz` **只回布尔**，不泄露账号池规模（曾实测上游会返回
  `total`，直接透传等于把池子大小告诉任何人）
- 网关 `/v1/*` 走独立的 API Key 鉴权（SQLite 密钥表），与管理端后台权限彻底分离

#### 会话与凭据
- `current_user` **只认签名 Cookie**：回查用户表（role 以表为准）、校验会话版本
  `sv`（改密/改角色/吊销后旧 Cookie 立即失效）、用户被删即拒绝
- 历史提权后门（`X-API-Key` 直接授予 admin）已彻底移除，并有 25 个守卫测试
- 密码 PBKDF2-SHA256 260k 轮 + 随机盐，比对用 `hmac.compare_digest`
- 登录防爆破**按 IP 与用户名双维度**计数；计数字典超限时**只淘汰过期条目**，
  绝不整体清空（否则攻击者灌满字典即可顺手抹掉 admin 的锁定计数）
- `users.json` 0600 + 原子写（临时文件 → fsync → `os.replace`）
- **API 密钥列表只返回前缀**，`key_hash` 从不回传

#### 注入类
- **SQL**：三处 f-string 拼接均为**硬编码列名**（迁移语句、`UPDATE ... SET` 的
  字段名来自本地白名单 dict），值全部走占位符 —— 无可注入点
- **命令**：全部 `subprocess` 调用为 **list 形式、无 `shell=True`**；
  从不把数据拼进 shell/Python 源码（上游曾因「把 OAuth 值拼进 heredoc
  的 Python 源码」出过注入，我们不具该形态）
- **路径穿越**：文件名走**白名单正则** `workbuddy-[0-9A-Za-z_-]{1,80}\.json`，
  且显式拒绝 `/`、`\`、`..`、`\x00`；静态文件走 `resolve()` + 包含判断
- **`upstream-ref`**：正则限制、首字符必须字母数字（无法构成 `-` 开头的选项注入），
  且以独立 argv 元素传给 git

#### 前端
- 无 `dangerouslySetInnerHTML` / `innerHTML` / `eval`
- Cookie `HttpOnly` + `SameSite=Lax`；**无任何 GET 写操作**（唯一带副作用的
  `/auth/poll` 需要服务端签发的 state，跨站无法构造）→ CSRF 面收敛
- 安全响应头齐全：CSP、`X-Content-Type-Options`、`X-Frame-Options: DENY`、
  `Referrer-Policy`、`Permissions-Policy`
- 前端不把任何凭据写入 `localStorage`/`sessionStorage`

#### 依赖与配置默认值
- `npm audit`：**0 漏洞**；`pip-audit`：**无已知漏洞**
- `/docs`、`/redoc`、`/openapi.json` **默认关闭**（`WB_ENABLE_DOCS=1` 才开）
- CORS 默认**不启用**（仅在配置了 `WB_CORS_ORIGINS` 时才挂中间件）
- SQLite 错误与上游错误**不透传内部细节**（只回状态码与布尔）

#### 其他
- 日志写入前统一 `_clean()`，剥离控制字符 —— 防**日志注入**（用换行伪造日志行）
- 更新目标为固定枚举 `manager|upstream|both`；更新包**核对发布页给的 sha256 与文件大小**
  （详见 [release-signing.md](release-signing.md)；本报告写于 2026-09-12，当时用的是
  离线私钥验签，2026-10-14 起改为摘要校验）；`deploy/` 不从包内自动替换

### 三、未修但需知悉

#### 1. 服务以 root 运行（设计权衡，非缺陷）

`deploy/workbuddy-web.service` 没有 `User=`，即服务以 root 运行。原因是它需要：

- 执行 `docker restart/logs`（操作上游容器）
- 写 `/opt/workbuddy-manager`
- 拉起更新脚本，而更新脚本需要 root（`systemctl restart`、`pip install`）

**为什么不改**：`docker` 组成员权限**等价于 root**（可挂载宿主根目录），所以
「加 docker 组 + 去 root」并不真正降低风险，反而增加部署复杂度。这是已知的
权衡，不是疏漏。

**真正有效的缓解**（部署方决定）：该服务**不要直接暴露公网**，藏在反向代理后
并只监听内网；`7864` 与 `7863` 都应收敛（安装脚本已自动收敛端口绑定）。

#### 2. `global.chat_base` / `billing_base` 可填内网地址（低危）

这两个配置项允许管理员指定任意 `http(s)://` 地址，服务端会向其发起请求。
理论上同样可用于内网探测，但：

- 它是**正常功能**（自建/第三方代理的场景需要自定义 base）
- 影响面小于 Upstash 测试：不是「探一个 URL 看回显」的原语，且改动会在
  后续所有上游调用中暴露（噪声大、难以隐蔽使用）

因此不收紧，仅在此记录。

#### 3. IP 白/黑名单**只作用于网关 `/v1/*`，不覆盖管理端 `/api/*`**

界面上「安全与 IP 管控」的语义是网关侧的访问控制。管理端的防护依赖：

- 强密码 + 双维度登录锁定（5 次 / 10 分钟）
- 「不要直接暴露 7864」（见上一节）

如果你的部署**必须**把管理端暴露到公网，建议在反向代理层加 IP 限制或
额外认证，不要只依赖应用内这条规则。

### 四、本轮新增的守卫测试

`server/tests/test_ssrf_guard.py`（6 个用例）：

- 内网/元数据地址（回环、私有段、链路本地、`169.254.169.254`、
  `metadata.tencentyun.com` 等）一律拒绝
- 公网主机（Upstash 官方与自建域名/公网 IP）**照常放行**，避免误伤正常功能
- 端到端断言「对内网目标**没有发出任何请求**」——只查返回值不够：
  返回失败但请求已发出时，探测已经成立
- 数据库主库与 `-wal`/`-shm` 均以 0600 收紧

反证已验：去掉主机校验 → 报红；放宽判定 → 报红；去掉 DB 权限收紧 → 报红。
